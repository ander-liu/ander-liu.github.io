# 前言

DDD 是个老话题了：聚合根、值对象、仓储、领域事件，概念大家都能背一串。可真写起代码来，很多项目还是老样子——Controller 里堆判断，Service 里直接调 Mapper，业务规则散落得到处都是。

概念和落地之间，隔的从来不是理解，而是一套“照着写就不容易跑偏”的工程约束。这篇文章整理我们在项目里落地 DDD 的整套做法：用一个六层结构划定边界，给每一层规定好职责与依赖方向，再把领域模型的写法固定下来。内容偏“规范”，但每条规矩背后都有它存在的理由。

# 六层骨架

项目拆成六个模块：facade、domain、infra、client、application、adapter。构建顺序是：

```
facade → domain → infra → client → application → adapter
```

依赖只允许单向往外走：

```
adapter → application → {client, domain, infra}；infra → domain → facade
```

六层各管一摊：

| 层 | 职责 | 依赖 |
| --- | --- | --- |
| facade | 与业务无关的基础类型：领域实体基类、事件 DTO 与发布接口等 | 无 |
| domain | 领域模型与领域逻辑；定义仓储 / 工厂 / 网关接口 | facade |
| infra | 实现 domain 的接口：持久化、外部调用、事件发布 | domain |
| client | 对外数据契约：Param / DTO / VO 与统一响应 Result | 无 |
| application | 用例编排：拿领域对象、调领域方法、划事务边界 | client、domain、infra |
| adapter | 入站适配：HTTP 控制器与事件消费者 | application、client |

有一点先说清楚：**domain 是重心，其余五层都在为它服务**——facade 给它提供基础类型，infra 提供实现，application 替它编排流程，adapter 帮它挡掉协议细节，client 把它的数据约定对外固定下来。方向定死了，代码就不会互相缠绕。

# 核心在 domain

domain 按业务领域划分子包，一个聚合一包。每个领域包的结构非常克制，**只允许四个子目录**：

```
domain/
├── common/                  # 跨领域：领域事件类型常量等
└── task/                    # 一个业务领域
    ├── Task.java            # 聚合根，放在包根
    ├── factory/             # 工厂接口
    ├── gateway/             # 网关接口
    ├── repository/          # 仓储接口
    └── valueobject/         # 值对象
```

query、dto、service 这类目录在这里是被禁止的，也没有“再开个文件夹放点别的”的余地。看着死板，但它保证了一件事：领域层里永远只有模型、接口和规则，不会长出别的东西。

## 聚合根：一切行为的入口

聚合根（比如 Task）放在领域包根目录，继承 facade 里的 DomainEntity，并且要完整实现它的全部抽象方法：domainValidate()、save(operatorId)、delete(operatorId)——不能只实现一部分，更不能留空。

它身上有几个“必须”：

```java
@Getter
@Setter
public class Task extends DomainEntity {
    private String num;                 // 业务编码
    private String title;
    private TaskStatus status;          // 状态由领域方法流转
    private List<TaskMember> members;   // 值对象集合

    private TaskRepository repository;
    private TaskGateway gateway;
    private DomainEventPublisher eventPublisher;
    // 构造方法传入必填字段与上述协作依赖，此处省略
}
```

- 必须有业务编码 **num**——领域对象的身份靠它，而不是数据库自增主键；num 为空时由网关生成；
- 必须把**仓储、网关、事件发布器**定义为属性——领域协作全靠它们；
- 必须有传入必填字段的构造方法，且**状态字段不进构造方法**——状态只允许通过领域方法流转；
- **不能有 is_deleted 这类软删除标记**——那是数据库的事，不该污染领域模型。

平时写业务，就是给聚合根加领域方法（save、updateTitle、close……）。校验和状态流转全部写在方法里，而不是散到 Service 层。

## 只有三个方法的仓储

domain 里的仓储接口是“三方法契约”，多一个都不行：

```java
public interface TaskRepository {
    void save(Task task);          // 保存，不区分新增与更新
    Task findByNum(String num);    // 按业务编码加载
    void deleteByNum(String num);  // 按业务编码删除
}
```

为什么这么吝啬？因为仓储只负责聚合的**生命周期**：加载一个领域对象、保存一个领域对象。至于“按标题模糊搜索”“按状态分页列表”这类查询，一概不进——它们走别的通道（后面会说）。接口足够小，就不会随业务增长而膨胀，领域层也不会被查询需求绑架。

另外，仓储是领域对象与工厂的内部协作接口，**application 层碰不到它**。写用例靠工厂拿对象，读用例走 QueryService，没有任何一层业务代码直接调用仓储。

## 工厂与网关

工厂接口只有两个方法，而且只能有两个：

```java
public interface TaskFactory {
    Task create(String title, String content);  // 用户创建时可能填写的字段
    Task createByNum(String num);               // 按业务编码加载
}
```

create(...) 的参数只收“用户创建这个对象时可能填的字段”，操作人、状态、审计字段一律不进；createByNum(...) 只做一件事：委托仓储的 findByNum 把既有对象加载出来。没有 createById，也没有 rebuild——领域对象的创建与加载路径各只有一条，不会出现旁门左道。

网关（gateway）负责剩下所有“对外”的事：生成业务编码是它的基本职责；凡是要碰第三方接口、权限校验，以及仓储三方法之外的读能力，都从这里定义接口，交给 infra 实现。

## 值对象

领域包里还有个 valueobject 目录，放值对象：比如任务成员（TaskMember）、任务流水（TaskRecord）这类只含业务属性、不继承 DomainEntity 的“贫血模型”。它们必须配齐 Lombok 五件套——@Getter、@Setter、@Builder、@AllArgsConstructor、@NoArgsConstructor，方便构造、序列化与 infra 映射。枚举之类则按业务需要定义。

## 六步顺序与领域事件

聚合根上任何会改变状态或产生持久化的方法——save、delete，以及 close、updateTitle 这类业务方法——必须严格走六步：

1. **初始化领域对象**（initialize）；
2. **领域规则校验**：比如“当前状态允不允许这个操作”；
3. **赋值与状态流转**：save 时若 num 为空，用网关生成；值对象为空则初始化；
4. **领域完整性校验**（domainValidate）；
5. **持久化**：调用 repository.save，不分新增与更新；
6. **发布领域事件**：

```java
domainEventPublisher.send(DomainEventDTO.builder()
        .type(DomainEventConstant.TASK_CREATED)
        .id(num)
        .data(this)
        .sender(operatorId)
        .build());
```

事件类型常量统一放在 domain/common 的 DomainEventConstant 里，命名跟业务语义一致（TASK_CREATED、TASK_CLOSED 等）。有个细节有点反直觉：**不允许用 wasNew 之类的标记去判断“只在新建时发事件”**——每次 save 都必须发，不做分支。事件是既成事实的记录，不是条件通知；要区分新建还是更新，用事件类型表达。

# application：只做编排，不做决策

application 层的规矩同样干脆：写用例一个 CommandService，读用例一个 QueryService，就这两个。

- **CommandService（写）**：通过 domain 的工厂拿对象（新建 create、加载 createByNum），再调领域方法（save、updateTitle……）。它自己不写任何领域规则，也**不允许注入仓储或网关**——领域协作是领域对象自己的事。事务边界在这里划：`@Transactional(rollbackFor = Exception.class)`。另外，涉及写操作的方法必须上 Redis 分布式锁，锁 key 基于业务标识（比如 num），并设置合理过期时间；顺序是**先拿锁，再开事务**。
- **QueryService（读）**：注入 infra 的 Mapper 做只读查询（用 LambdaQueryWrapper），结果转成 client 的 DTO 返回。查询不经过领域模型，也就不会为了一个列表页去惊动整个聚合。

两条硬性约定：方法入参必须用类封装（client 层的 XXXParamDTO），不允许裸的 String、Long 参数；返回值必须是 client 层的 DTO，不返回实体，也不返回 VO——VO 是 adapter 的事，application 不认识它。

# infra 与 adapter：一个实现，一个门面

**infra** 是所有接口的唯一实现地。按领域分包，每包里有 entity（表映射 PO，@Data + 逐字段注释）、mapper、repository、factory、gateway 五个角色；跨领域的东西（事件发布实现、常量、工具、外部 HTTP 客户端）统一放 common。两条硬约束值得一提：

- RepositoryImpl **只准注入 Mapper**——不能有事件发布器，不能有网关；“存在性判断”一律按 num 查库；
- FactoryImpl **只准注入本聚合的仓储**，且只实现 create、createByNum 两个方法。

is_deleted 这样的字段只活在 entity 和数据库里，绝不映射到领域模型——领域对象压根不知道“软删除”这回事。

**adapter** 是入站层，薄到不能再薄：Controller 负责收 Param（配合 @Valid 校验）、转 VO、返回 Result；listener 负责收事件、调 application。config 下默认有三件套：BaseController（从请求里取当前用户）、GlobalExceptionHandler（统一兜底成 Result.fail）、TokenValidationFilter（认证）。启动类放在 adapter 包根。前端协议的细节全被挡在这一层，application 以下感受不到 HTTP 的存在。

# 一条请求的完整旅程

把上面的东西串起来，看一次“创建任务”：

1. TaskCommandController 收到 TaskCreateParam（@Valid 校验），从 BaseController 拿到当前用户 ID；
2. 调用 TaskCommandService.create(param, operatorId)：先拿 Redis 锁，再开事务；
3. CommandService 通过 taskFactory.create(title, ...) 造出新的 Task；
4. 调 task.save(operatorId)，六步走完：初始化 → 校验 → 赋值（num 缺席则用网关生成）→ 完整性校验 → repository.save → 发 TASK_CREATED 事件；
5. 返回 TaskDTO；Controller 把它转成 TaskVO，包进 Result.ok(...)。

读的路径更短：TaskQueryController → TaskQueryService → Mapper → TaskDTO → TaskVO → Result。

从 HTTP 到数据库这整条链路里，领域规则始终只在 domain 层出现一次。

# 几个“为什么”

几条最容易被问“为什么这么严”的规矩，单独说说理由：

**仓储为什么只有三个方法？** 查询需求是发散的，今天加个分页，明天加个统计，仓储接口迟早爆炸；把读剥离出去（QueryService + Mapper），仓储永远是“加载—保存—删除”三件事，领域层的依赖面就不会扩大。

**工厂为什么只有两个方法？** 创建入口越少，领域对象的组装越可控。createByNum 只允许委托 findByNum，意味着“加载”永远走仓储这一条路，不会出现某个实现偷偷绕过仓储拼对象的情况。

**application 为什么不能碰仓储和网关？** 这两个是领域内部的协作接口。application 的职责是编排：工厂拿对象 → 调方法 → 返回 DTO。一旦允许它直接查仓储、调网关，领域规则就会开始往外漏，最后又是熟悉的“业务逻辑散落各处”。

**为什么每次 save 都发事件？** 没有“新建才发、更新不发”这种分支，事件语义才简单：发生了就是发生了。要区分新建还是更新，用事件类型（CREATED / UPDATED）表达，而不是靠条件逻辑。

**为什么领域模型没有 is_deleted？** 软删除是一种存储策略，不是业务概念。业务关心的是“这个任务还在不在”，存储关心的是“这行数据怎么标记”。两者混在一起，领域模型就被数据库细节污染了。

# 小结

以上就是我们落地 DDD 的整套做法：六层结构划定边界，domain 承载模型与规则，仓储、工厂、网关把领域与外部的协作收敛成极小的接口，领域事件保证每次状态变化都可被感知，application 只编排不决策，infra 兜住所有实现，adapter 挡住所有协议细节。

概念谁都会讲，难的是让它每天都在代码里发生。这些看起来“死板”的约束——仓储只有三个方法、工厂只有两个方法、目录只许四个——恰恰是把 DDD 从 PPT 里拽进工程现实的那根绳子。
